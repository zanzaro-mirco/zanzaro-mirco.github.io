choices:
  - title: One codebase for the wire, in C
    text: >-
      The frame and the CRC live once, in C: the firmware and the Android plugin (through JNI)
      use them, and the Swift side will too. The expected bytes in the tests are not computed
      by our code but by Python's standard library: a vector generated by the code under test
      would be wrong along with it.
  - title: Three outcomes, not two
    text: >-
      If the connection drops before the response, the write is uncertain. Every write carries
      the revision it is based on, like an ETag: repeating it does not apply it twice, and a
      late retry does not overwrite a newer change. The app shows as the current value only
      what has been confirmed.
  - title: One GATT operation at a time
    text: >-
      Android's GATT runs one operation at a time, and a second one requested too early is
      rejected or lost, depending on the phone. A pure Kotlin queue lines them up, and every
      operation has a key: the late callback of an expired one does not complete the next.
      It is tested on the JVM with a fake clock.
  - title: The failure, tested on hardware
    text: >-
      The debug firmware has a command that saves the change and reboots the board without
      responding. With the board and a Galaxy S20, the app showed “Change not confirmed”, and
      the check got “already applied”: the revision moved forward by one, not two.
lesson: >-
  Faced with an uncertain write, reading the state again and building a new request looks like
  the careful choice, and it is the wrong one: if the first write got through, the second
  applies it again. When I removed the safeguard, two tests turned red with the revision two
  steps ahead. The retry has to be the same request.

  - The hardware test was done by hand, with a single board and a single phone.
  - >-
    The test of the C code called through JNI runs on an emulator in CI, but it has not been
    falsified.

Whoever installs an automation system, a controller or a pump configures it from a phone, on
site, often with a Bluetooth link that comes and goes. When the connection drops halfway
through a write, the app does not know whether the controller applied the value.

Treating it as failed leads the installer to try again, and a late retry can overwrite a newer
change. Treating it as successful shows a value the controller may not have. Here uncertainty
is an outcome of its own, and it is resolved safely.
